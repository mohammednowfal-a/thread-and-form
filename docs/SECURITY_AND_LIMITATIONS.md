# Security model and known limitations

## What is enforced
* **Server is the source of truth** for price, variant, stock and totals; browser-supplied totals are ignored (tested).
* **AuthN**: bcrypt (cost 12) passwords, opaque random session tokens stored only as HMAC hashes, httpOnly + SameSite=Lax (+ Secure in production) cookies, expiry and revocation,
  constant-time failure path, DB-backed rate limits (login, register, checkout, tracking, reset, webhooks), password reset invalidates all sessions.
* **AuthZ**: every admin page and server action calls `requireStaff(permission)`; roles are checked on the server (tested with UI bypassed).
* **Tenant isolation**: tenant comes from the signed-in user's verified membership; every query/mutation is scoped by `tenantId`; composite unique keys are tenant-scoped (tested).
* **CSRF**: mutations are Next.js Server Actions (framework origin checks) plus SameSite=Lax cookies. Public API routes (webhooks, jobs) use no cookies and authenticate by signature/secret.
* **Webhooks**: HMAC-SHA256 signature, constant-time compare, size limits, idempotent storage, replay tooling. Shipping webhook: shared-token header.
* **AI/chat safety**: customer text is untrusted. Order confirm/cancel is deterministic (buttons or short unambiguous replies, ownership by sender phone). The optional AI provider can only classify questions; it cannot touch orders.
* **Privacy**: secrets only in env vars; logs and audit entries scrub secrets; tokens never stored in errors (tested); phone numbers are masked in the customer and conversation lists; retention job purges old webhook events/sessions/rate-limit rows hourly.
* Security headers (HSTS, nosniff, frame deny, referrer, permissions policy). No inline-script CSP yet (see below).

## Known limitations (be aware before launch)
* **Not verified in a real browser.** The build environment could not download browsers. Playwright specs exist (`tests/e2e`) but were never run. Mobile/desktop layout was built mobile-first with Tailwind but not visually verified; run the e2e suite and review on real devices.
* **Not verified against live providers**: WhatsApp (Meta), Shiprocket, Delhivery, Shopify, the email provider and the AI provider are implemented to their public docs and tested with mocks only.
* **WhatsApp credentials are environment-level**: one WhatsApp number/token per deployment. Inbound messages are routed to a tenant by `phone_number_id` (via `IntegrationAccount.config.phoneNumberId` or the env number), but outbound sending uses the env token. Per-tenant tokens need a secrets store.
* **Storefront serves one tenant per deployment** (`STOREFRONT_TENANT_SLUG`). The admin supports many tenants/memberships, but there is no tenant switcher: a user lands in their first membership.
* No online payments (COD only), no discount codes, no tax engine (prices are tax-inclusive), no email verification flow, no product-image upload (URLs only), no returns refund automation.
* Product photos are generated illustrations (SVG), not photography. Replace via Admin → Products.
* Policy pages are templates and need review by a qualified professional.
* Migrations were generated by script (see `DEPLOYMENT.md` for the drift check). The Prisma client uses the driver-adapter engine (`engineType = "client"` with `@prisma/adapter-pg`).
* `npm audit` reports advisories in build tooling (Prisma CLI's config loader, and PostCSS bundled in Next 15). Fixes are major upgrades (Prisma 7, Next 16); plan them. They are not reachable by request traffic.
* Content-Security-Policy is not set (it needs nonce handling for Next's inline scripts); add one if your threat model requires it.
